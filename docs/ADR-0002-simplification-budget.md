# ADR-0002：哪些可以砍，哪些不能砍

- 状态：已采纳
- 日期：2026-09-18

## 背景

首要目标是「任务顺利、安全、高效地执行」，而非功能完备。
此前的实现方式是在主线程直接开后台任务，随任务类型增多不断加锁，
最终不可维护。需要明确本架构中哪些部分是地基、哪些是可选装饰。

## 诊断

不可维护的根因不是"没用对框架"，而是**状态在内存里**。

多个 goroutine 争抢同一份内存状态（谁在跑、跑了几个、轮到谁），
就必须用锁维护一致性，而锁的组合数随功能数平方增长。

本架构的解法不是"换更好的锁"，而是把状态搬出内存：
谁能跑、跑了几个、轮到谁，全部由 `Claim` 那一条 SQL 的原子性决定。
结果是**全代码库零 `sync.Mutex`**。

## 决定

### 不能砍（砍了要重写）

| 机制 | 砍掉的后果 |
|---|---|
| 原子 `Claim` | 退回内存锁，回到原点 |
| 租约 + Reaper | 一次 `kill -9` 就要人工改数据库状态 |
| `Job` 状态机 | 状态迁移散落各处，无法保证合法性 |
| `Batch` 聚合 | 答不出"整体进度"和"整单取消" |
| `job_events` | 出问题时只看得到 `state='dead'`，看不到原因 |

关于 `job_events` 的成本，常被高估。它是一张只追加的表：
代码量是一个 `INSERT`，没有状态机，没有并发问题，
与状态变更在同一事务内因而天然一致。它是全套机制里最便宜的部分。

### 可以砍（将来加回来无痛，因为只加字段不加概念）

| 可砍项 | 怎么砍 | 何时加回 |
|---|---|---|
| `priority` | 全填 0，`ORDER BY` 保留 | 出现"插队"需求时 |
| `rate_limited` 车道 | 只配 `serial` + `pool` | 要限流调外部 API 时 |
| `Scope` 展开 | 只实现 `explicit`（直传 ID 列表） | 要"按班派发"时实现 expander |
| 进度落库 | 保持 `group by` 聚合 | 数据量大到聚合变慢时（很久以后） |

## 后果

砍掉可砍项后，调度内核的必要代码约在 1000 行量级，
且不含任何并发原语——并发正确性完全由数据库事务保证。
