# ADR-0001：调度内核的技术选型

- 状态：已采纳
- 日期：2026-09-18

## 背景

需要对「一组数据上的动作」做异步调度。典型场景：学校体检（CT 串行独占、
血常规多护士并行、按班/全校派发）、照片库批量 AI 分析（GPU 独占）、
缩略图、抽元数据、限流调外部 API。

要求：批量派发、排队执行、状态查询、失败重试、过程留底、多种触发方
（终端用户 / 管理员 / 系统事件 / 定时任务）。业务数据目前在 SQLite。

评估了两个候选：

- **方案 A**：Go 自研调度内核，关系库作为事实源
- **方案 B**：Python + FastAPI + Celery + Redis

## 关键判断：两个方案不在同一层

这是本次决策的核心认识。

- 方案 A 回答的是：**任务的事实源放在哪里，领域模型长什么样**
- 方案 B 回答的是：**任务用什么运输和执行**

Celery 不是方案 A 的替代品，它是方案 A 架构中「队列 + worker 进程管理」
那一格的一个实现。因此"二选一"的提法不成立，应当拆成两个独立问题。

### 问题一：事实源放哪里？

**决定：关系库。**

需求里的「批量进度、整单取消、失败重试、过程留底、按触发方筛选、按班派发」
全部是查询需求。Redis Result Backend 是一个带 TTL 的 KV，
它无法回答"三班 42 人体检到哪一步了"，也无法在重启后保留这些信息。

这一条没有讨论空间。方案 B 常见示例中「状态主要放在 Redis result +
业务单据字段」的做法，直接不满足需求。

### 问题二：用什么运输和执行？

**决定：Go 自研，不引入 Celery / Redis。**

推论如下：一旦事实源定在数据库，Celery 最有价值的能力
（可靠投递、重试、路由）就已经被重新实现了一遍——因为问题一强制要求如此。
此时 Redis 的剩余作用仅是「新任务到达的通知信号」，
而这个作用可以用轮询间隔替代（代价：首个任务最多延迟 `SCHED_POLL_INTERVAL`）。

用 `SELECT ... FOR UPDATE SKIP LOCKED`（PostgreSQL）或
`BEGIN IMMEDIATE` + 条件 UPDATE（SQLite）加租约机制，
约 200 行 Go 代码即可覆盖，并且**少一个必须运维的有状态组件**。

### 但方案 B 有一点是对的：GPU 推理该用 Python

**决定：切开，两边各用所长。**

```
Go 调度内核（batch / lane / 租约 / 重试 / 审计）
      │  HTTP
      ▼
Python 推理服务（无状态，只暴露 target → 结论）
```

推理服务不感知调度语义：没有 job 状态、没有重试、没有队列。
它崩溃了，租约到期后 Reaper 会把任务放回队列。

这样一来「团队主栈是 Python 还是 Go」不再需要裁决：
算法同学写 `predict(target) -> result`，服务端同学写调度，两边不必互相学栈。

## 存储决定

**调度库独立于业务库，现阶段两者都用 SQLite，但是两个独立文件、独立迁移。**

理由：SQLite 的 `BEGIN IMMEDIATE` + 条件 UPDATE 与 PostgreSQL 的
`SKIP LOCKED` 在语义上等价（都是「原子地抢一个任务」）。
只要仓储接口切干净，换库就是换一个包。

为此付出的设计代价只有两处：时间统一存 Unix 毫秒整数；SQL 全部收敛在
`sqlstore` 包内。

**触发换库的信号只有一个：多机部署 worker。** 同机多进程共享一个 SQLite
文件可行（WAL 模式），跨机器则必须换 PostgreSQL。
判据不是"将来可能换"，而是"哪天要多机"。

## 后果

正面：

- 全代码库零 `sync.Mutex`。资源竞争由数据库事务语义解决，
  而非由内存锁解决——后者的锁组合数随功能数平方增长，是不可维护的根因。
- 部署面小：两个 Go 二进制 + 一个 SQLite 文件（+ 可选的 Python 推理服务）。
- 批量、审计、多触发、幂等是领域模型的一部分，不是事后补的开关。

负面与代价：

- 队列与重试要自己实现（已实现并有并发测试覆盖），
  工作量大于直接套用 Celery 示例。
- 车道空闲时靠轮询，首个任务最多延迟一个轮询周期。
  若将来要求亚秒级启动延迟，可加 Redis / `LISTEN-NOTIFY` 作为通知加速层，
  但事实源仍在数据库。
- 需要团队能维护 Go 服务。若团队完全没有 Go 经验，前期有学习成本；
  但调度内核的代码面很窄（领域 + 用例约 1000 行），且不涉及算法栈。

## 已验证的正确性底线

见 `internal/adapter/outbound/sqlstore/claim_test.go`：

- 20 个 goroutine 同抢一条 `serial` 车道，有且只有一个拿到任务
- `pool` 车道不超发
- 过期租约不会永久堵死车道（即使 Reaper 尚未运行）
- 相同幂等键的重复提交被折叠成一个任务

`internal/adapter/inbound/worker/pool_test.go`：

- `pool` 车道的实际并发峰值等于配置容量
- `serial` 车道的实际并发峰值恒为 1

后两条针对一个真实出现过的缺陷：数据库里的容量校验只是上限保证，
它能拦住超发，却制造不出并发。车道容量要兑现成吞吐，
必须在 worker 侧起对应数量的取号 goroutine。**上限和并发是两件事。**

端到端另已验证：GPU 车道执行期间 `running` 恒为 1；
失败任务按指数退避自动重试；整单取消时正在执行的任务结果被正确丢弃；
接入远程推理 API 时，实测打到对方服务的并发峰值精确等于车道容量。
